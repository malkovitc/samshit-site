# Развёртывание на sd-105293

Каталог на боксе: `/data/samshit` (клон репозитория). Секреты в `deploy/.env` (не в git).

```sh
cd /data/samshit/deploy
docker compose up -d --build postgres redis backend
docker compose exec backend yarn medusa exec ./src/scripts/seed.js   # один раз, печатает ключ витрины
docker compose exec backend yarn medusa user -e <email> -p <password>  # админ
# вписать MEDUSA_PUBLISHABLE_KEY в .env, затем
docker compose up -d --build storefront
```

Предпросмотр до публикации: `ssh -L 18000:127.0.0.1:18000 -L 19000:127.0.0.1:19000 sd-105293`,
витрина http://localhost:18000, админка http://localhost:19000/app.

Обновление только витрины, не перезапуская бэкенд:

```sh
cd ~/samshit && git pull && cd deploy && docker compose up -d --build --no-deps storefront
```

Каталог на самом деле `~/samshit`. Не выкатывать во время релиза Linza: её гейт проверяет хосты магазина.

## Оплата (Bank of Georgia)

Пока нет договора эквайринга, в `.env` стоит `BOG_MOCK=true`: бэкенд сам изображает банк
(`/mock-bog/*`, страница «оплаты» с пометкой Test mode), через неё проходит настоящий код провайдера.
Когда банк выдаст ключи:

```sh
# в deploy/.env: BOG_MOCK=false, BOG_CLIENT_ID=..., BOG_CLIENT_SECRET=...
docker compose up -d --no-deps backend
docker compose exec backend yarn medusa exec ./src/scripts/enable-bog.js   # если регионы ещё без pp_bog_bog
```

В кабинете мерчанта банка включить способы: карта, Apple Pay, Google Pay. Колбэк банк шлёт на
`https://samshit-api.linza-ai.xyz/hooks/payment/bog_bog` (адрес задаётся в каждом заказе).

## Пароль сотрудника

Не через `-p` в командной строке (виден в `ps`): см. `backend/src/scripts/set-admin-password.ts`.

## Добавление товаров владельцем

Войти в Medusa Admin (`/app`) под отдельной учётной записью владельца и открыть **Товары Самшит**.

1. Нажать **Новый товар**. Для черновика нужны адрес товара латиницей, артикул, категория и русское название.
2. Заполнить название, конструкцию и материал на русском, английском и грузинском. Добавить фото; первое станет обложкой. Порядок меняется стрелками.
3. Указать цены отдельно в USD, EUR и GEL. Для MTM включить вариант при создании товара и задать его цены. В существующем товаре можно менять цену MTM, но не добавлять или удалять сам вариант.
4. Указать готовые остатки S–XL на складе в Тбилиси, срок пошива, при необходимости тираж и дату предзаказа. Нулевой остаток означает пошив под заказ. Дата предзаказа показывается покупателю, но не закрывает оформление заказа.
5. Нажать **Сохранить черновик** или **Опубликовать**. При публикации форма покажет недостающие поля. Для опубликованного товара кнопка **Обновить товар** проверяет и сохраняет изменения без снятия с витрины; кнопка **Снять с публикации и сохранить черновик** скрывает его до повторной публикации.

В списке доступны исходные товары и действие **Дублировать**. Дубликату нужно задать новый адрес и артикул; остатки у него начинаются с нуля. Для обновления товаров seed-скрипт не запускать: он предназначен только для пустой базы.

## Фото товаров в production

Локальный файловый провайдер Medusa хранит новые загрузки в томе `static` и подходит для разработки. До передачи загрузки фото владельцу настроить S3-совместимое хранилище: в `deploy/.env` задать `S3_FILE_URL`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_REGION`, `S3_BUCKET` и при необходимости `S3_ENDPOINT` и `S3_FORCE_PATH_STYLE=true`. `S3_FILE_URL` должен быть публичным HTTPS-адресом файлов. Если задан `S3_FILE_URL`, бэкенд при старте проверит остальные обязательные переменные. Ключи не добавлять в git.

После переключения на S3 старые фото с путями `/static/...` продолжат загружаться из тома `static`; его нельзя удалять. Перед выкладкой сделать резервную копию базы Medusa и тома `static`, затем проверить восстановление и загрузку нового фото. После пересборки бэкенда открыть фото нового товара и убедиться, что оно доступно по публичному URL.

Проверить права доступа владельца к Admin отдельно: в текущей Medusa без Enterprise RBAC учётная запись Admin имеет доступ не только к товарам.
